# Проект `models` — сервисы с моделями и GPU

**Что это.** Локальные модели для RAG и лестницы решений: **эмбеддинги** (`llama.cpp`, порт `8082`) и
**решатель** `solver` (порт `8083`) — имя по РОЛИ, а не по модели. Своя папка, свой композ, свой лончер,
свой набор образов.

**Чего здесь нет.** Прикладного кода продукта: проект — обвязка вокруг моделей (композ, лончер,
Dockerfile'ы, замер паритета). Модели — не часть продукта, а служба общего назначения.

## Как запускать

```bash
cp .env.example .env   # заполнить пути к модели и ключам (см. ниже)
make up                # снять конкурирующие хостовые юниты и поднять оба сервиса
make status            # проверить, отвечают ли оба адреса
make stop              # остановить (откат на хостовые юниты — см. вывод команды)
make check             # офлайн: композ разбирается настоящим парсером
make images            # собрать оба образа (нужны исходники llama.cpp и решателя, см. ниже)
make parity            # замер паритета эмбеддингов: два адреса, числа на выходе
```

## Контракт с остальными

* **Сеть — общая с платформой** (`external: true`, имя в `PLATFORM_NETWORK`): создаёт её стек платформы,
  проект её не создаёт.
* **Имена служб внутри сети — контракт**: `embed` (`http://embed:8082/v1`) и `solver`
  (`http://127.0.0.1:8083`). К ним приходят по этим адресам, поэтому имена менять нельзя.
* **Порты публикуются только на `127.0.0.1`** — наружу отдавать нечего.
* **Своего состояния у проекта нет**: тома — только монтирования снаружи (модель, ключи), поэтому
  привязанных к имени проекта томов здесь нет.

| Служба | Адрес | Что это |
|---|---|---|
| `embed` | `127.0.0.1:8082` | эмбеддинги: `llama-server` с CUDA, модель монтируется снаружи |
| `solver` | `127.0.0.1:8083` | локальный решатель лестницы решений, GPU |

## Что нужно снаружи

Оба образа собираются ИЗ ГОТОВЫХ БИНАРНИКОВ, собранных на хосте, — не компилируют llama.cpp заново:

* **`LLAMA_SRC`** — каталог `llama.cpp`: бинарники `src/llama.cpp/build-embed` (контекст сборки образа
  эмбеддингов), файл модели и `api_keys.txt`.
* **`SOLVER_SRC`** — каталог решателя: его исходники, `_build/llama.cpp-pinned` и бинарник
  `jev-score-v2`.

Пути задаются переменными и **не имеют умолчаний в репозитории**: чужой раскладки здесь нет. Файлы модели
и ключей монтируются в контейнеры по путям, которые ждут сами сервисы: эмбеддинги — `/models-src/…`,
решатель — `/keys/api_keys.txt` (жёстко зашитый в его коде путь перекрыт при сборке образа и читается из
`JEV_KEY_FILE`, см. `solver/Dockerfile`).

```bash
LLAMA_SRC=/path/to/llama.cpp bash embed-image.sh
SOLVER_SRC=/path/to/solver bash solver-image.sh
```

Сборщики сверяют эталоны — ревизию исходников `llama.cpp` и `sha256` файла модели — и падают при
расхождении: без этого через неделю никто не скажет, чем собран работающий образ.

## Окружение

Значения читаются из `.env` рядом с композом (образец — `.env.example`). Ключи, которые нужны всегда:
`PLATFORM_NETWORK`, `EMBED_MODEL_FILE`, `LLAMA_KEYS_FILE`; для решателя — `SOLVER_KEY_FILE`. Теги образов
переопределяются `EMBED_IMAGE`/`SOLVER_IMAGE`, квантование решателя — `JEV_QUANT`/`JEV_NGL`.

## Чего в проекте намеренно нет

* **Сторожей и юнитов** — наблюдение живёт в обвязке воркспейса, таймеры хостовые; этого репозитория они
  не касаются.
* **Пакета на Python и тестов** — проверяется то, что есть: разбор композа, синтаксис лончеров, линтер
  одного скрипта (`infer-parity.py`), доступность обоих сервисов.
* **`--remove-orphans`** — запрещён: он удаляет контейнеры, которых нет в ЭТОМ файле.
